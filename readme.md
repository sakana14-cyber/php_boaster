# 給与タイマーアプリ AIコーディング共通ルール

## 1. プロジェクトの目的

このアプリは、アルバイト・パートなどで働くユーザーが、

* 時給を設定する
* 「出勤」ボタンを押して勤務開始
* 「退勤」ボタンを押して勤務終了
* 勤務中の予測給与をリアルタイムで確認する
* その日の確定給与を確認する
* カレンダーから日ごとの給与を確認する
* 月間給与を確認する

ことができる勤怠・給与可視化アプリである。

最も重要な体験は、

「出勤ボタンを押すだけで、今いくら稼いでいるのか分かる」

ことである。

機能追加・UI設計・データ設計を行う場合は、この目的を最優先すること。

# 2. 最重要原則

以下の優先順位で設計する。

1. 操作が簡単
2. 給与計算が正確
3. 現在の給与が分かりやすい
4. スマートフォンで使いやすい
5. データが消えない
6. 後から機能追加しやすい
7. コードが初心者にも理解しやすい

複雑な操作や不要な設定項目を増やさないこと。

# 3. 基本機能

最低限、以下の機能を実装する。

## 時給設定

ユーザーは自分の時給を設定できる。

例：

時給：1,200円

時給は整数で保存する。

0円以下の時給は登録できない。

## 出勤

「出勤」ボタンを押した時刻を勤務開始時刻として記録する。

例：

2026-09-02 09:03:24

勤務中の場合は、二重に出勤できないようにする。

## 退勤

勤務中に「退勤」ボタンを押すと、その時刻を勤務終了時刻として記録する。

勤務していない状態では退勤できない。

## 勤務中タイマー

勤務中は、

勤務時間

と

現在の予測給与

をリアルタイムで表示する。

例：

勤務時間
03:21:42

現在の給与
4,034円

# 4. 給与計算ルール

給与計算は必ず時間ではなく「秒」を基準に行う。

基本計算式：

給与 = 時給 × 勤務秒数 ÷ 3600

例：

時給1,200円

1時間30分勤務

勤務秒数：

5400秒

給与：

1200 × 5400 ÷ 3600
= 1,800円

# 5. 表示用給与と確定給与

勤務中に表示する給与は「予測給与」とする。

退勤後に保存された給与を「確定給与」とする。

勤務中：

予測給与
3,421円

退勤後：

本日の給与
6,842円

のように区別する。

# 6. 端数処理

内部計算では可能な限り正確な値を保持する。

画面表示では原則として1円未満を切り捨てる。

例：

1234.8円

↓

1,234円

端数処理方式はコードの複数箇所に直接記述せず、共通処理として実装すること。

# 7. 時給変更時のルール

過去の勤務記録の給与が、現在の時給変更によって変わってはいけない。

そのため勤務記録には、

* 勤務開始時刻
* 勤務終了時刻
* その勤務に適用された時給
* 勤務時間
* 給与

を保存する。

例：

9月1日
時給1,100円
給与5,500円

9月2日に時給を1,200円へ変更しても、

9月1日の給与5,500円は変更しない。

# 8. 勤務データ

1回の勤務記録は最低限以下の情報を持つ。

* ID
* ユーザーID
* 出勤日時
* 退勤日時
* 適用時給
* 勤務秒数
* 給与
* 作成日時
* 更新日時

勤務中の場合、退勤日時はNULLを許可する。

# 9. カレンダー

カレンダーでは日付ごとの給与を表示する。

例：

9月1日
5,430円

9月2日
6,820円

9月3日
休み

同じ日に複数回勤務した場合は合計金額を表示する。

例：

09:00〜12:00
3,600円

17:00〜20:00
3,600円

カレンダー：

9月2日
7,200円

# 10. カレンダーの日付詳細

カレンダーの日付を押した場合、その日の勤務詳細を確認できるようにする。

表示内容：

* 出勤時間
* 退勤時間
* 勤務時間
* 適用時給
* 給与

例：

9月2日

09:03〜15:12

勤務時間
6時間9分

時給
1,200円

給与
7,380円

# 11. 月間給与

現在表示している月の給与合計を表示する。

例：

2026年9月

今月の給与

82,430円

勤務時間

68時間42分

勤務日数

12日

# 12. ホーム画面

ホーム画面では情報を詰め込みすぎない。

最優先で表示するものは以下。

勤務していない場合：

今日の給与

0円

[ 出勤する ]

勤務中：

勤務中

03:42:18

現在の給与

4,445円

[ 退勤する ]

その下に、

今月の給与

今月の勤務時間

などを表示する。

# 13. 出勤ボタン

出勤ボタンはホーム画面で最も目立つ操作にする。

ユーザーがアプリを開いてから、

1〜2回以内の操作で出勤できる

ことを目標とする。

不要な確認ダイアログは表示しない。

# 14. 退勤ボタン

勤務中は「出勤」ではなく「退勤」をメインボタンとして表示する。

誤操作防止のため、

出勤中

であることが画面上ですぐ分かるデザインにする。

# 15. リアルタイム給与

勤務中の給与表示は一定間隔で更新する。

ただし、

1秒ごとにAPIへアクセスしてはいけない。

サーバーから取得した

* 出勤時刻
* 時給

を元に、現在時刻との差をフロントエンド側で計算して表示する。

確定値は退勤時にサーバー側で再計算する。

# 16. サーバーを正とする

給与や勤務時間など重要なデータについて、

フロントエンドから送られてきた計算結果を信用してはいけない。

給与の確定計算は必ずサーバー側で行う。

例：

フロントエンド

「給与は8,000円です」

という値を送信しても、その値をそのままDBへ保存しない。

サーバー側で、

出勤時間
退勤時間
適用時給

から再計算する。

# 17. 時刻管理

DB上の日時は一貫したタイムゾーン管理を行う。

ユーザーへの表示は日本時間を基本とする。

タイムゾーン：

Asia/Tokyo

日付判定・カレンダー集計でタイムゾーンのズレが発生しないようにする。

# 18. 日付をまたぐ勤務

勤務が日付をまたぐ可能性を考慮する。

例：

9月2日 22:00

↓

9月3日 02:00

この場合でも勤務時間が正しく計算されること。

日別給与をどの日に計上するかについては、原則として勤務開始日を基準とする。

ただし将来的に日付単位で分割できる設計を意識する。

# 19. データ整合性

以下の状態を許可しない。

* 同じユーザーが同時に複数の勤務を開始する
* 退勤時間が出勤時間より前
* 時給0円以下
* 勤務時間がマイナス
* 給与がマイナス
* 存在しない勤務を退勤する
* 他ユーザーの勤務記録を変更する

# 20. 多重クリック対策

ユーザーが出勤・退勤ボタンを連打しても、複数の勤務記録が作成されないようにする。

ボタン押下後は処理完了まで無効化する。

サーバー側でも二重登録を防止する。

# 21. 編集機能

将来的に勤務時間を修正できるようにする。

例：

実際

09:00

間違えて

09:15

に出勤を押してしまった場合、

勤務履歴から修正できる。

修正した場合は給与も再計算する。

# 22. 削除機能

勤務記録を削除する場合は確認を表示する。

例：

「9月2日の勤務記録を削除しますか？」

削除後は月間給与・カレンダー表示を再計算する。

# 23. UIデザインルール

デザインは、

シンプル
モダン
スマートフォン優先

とする。

装飾よりも情報の読みやすさを優先する。

特に、

現在の給与

を最も大きく表示する。

# 24. 金額表示

給与は日本円形式で表示する。

123456

ではなく、

123,456円

とする。

# 25. 時間表示

勤務時間は状況に応じて、

03:42:18

または

3時間42分

のように分かりやすく表示する。

# 26. レスポンシブ対応

スマートフォンを最優先に設計する。

最低限、

* iPhone
* Android
* PC

でレイアウトが崩れないようにする。

横スクロールが発生するUIは原則禁止。

# 27. データ取得

画面表示のために必要以上のデータを取得しない。

カレンダーの場合は表示中の月を中心に取得する。

全勤務履歴を毎回取得する実装は避ける。

# 28. コード構造

巨大な1ファイルを作らない。

役割ごとに、

* UI
* ビジネスロジック
* API
* DBアクセス
* 給与計算

を分離する。

給与計算処理は共通化する。

# 29. DRY原則

同じ処理を複数箇所にコピーしない。

特に、

* 給与計算
* 時間計算
* 金額フォーマット
* 日付フォーマット

は共通関数・サービスとして管理する。

# 30. 命名規則

変数名・関数名・クラス名は意味が理解できる名前にする。

悪い例：

a
data2
aaa
test123

良い例：

hourlyWage
clockInTime
clockOutTime
workedSeconds
estimatedSalary

# 31. コメント

コードを読めば分かる内容を大量にコメントしない。

複雑な計算や、

「なぜこの実装にしているのか」

が分かりにくい部分のみコメントする。

# 32. 初心者が理解できるコード

必要以上に高度な抽象化を行わない。

短く書くことより、

読みやすいこと

を優先する。

AIがコードを生成する場合も、保守しやすいシンプルな実装を優先する。

# 33. エラーハンドリング

通信失敗や保存失敗を無視しない。

例：

「出勤記録の保存に失敗しました。もう一度お試しください。」

など、ユーザーに分かる形で表示する。

エラー発生時に画面が真っ白にならないようにする。

# 34. ローディング

API通信中はユーザーに処理中であることを伝える。

特に出勤・退勤処理では、

ボタン連打防止

と

ローディング表示

を行う。

# 35. 認証

ユーザー機能を実装する場合、

すべての勤務記録はログインユーザーに紐付ける。

ユーザーAがユーザーBの、

* 給与
* 時給
* 勤務履歴

を閲覧・変更できないようにする。

# 36. セキュリティ

入力値を信用しない。

必ずサーバー側でもバリデーションする。

SQLインジェクション、XSS、CSRFなど一般的なWebアプリの脆弱性を防止する。

# 37. DB変更

既存のDBデータを破壊する変更を安易に行わない。

カラム追加・変更時はマイグレーションを使用する。

既存データへの影響を確認する。

# 38. AIによるコード変更ルール

AIは既存コードを変更する前に、

1. 現在の構造を確認
2. 関連コードを確認
3. 変更による影響範囲を考える
4. 必要最小限の変更を行う
5. エラーがないか確認

という順番で作業する。

# 39. 勝手な仕様変更禁止

AIはユーザーから指示されていない既存仕様を勝手に変更してはいけない。

新しい機能を実装するために既存機能を削除してはいけない。

仕様上判断が必要な場合は、このルールに最も沿った方法を選択する。

# 40. 既存コード優先

既に正常に動作しているコードがある場合、

全面的な書き換えより、

既存構造を活かした変更

を優先する。

# 41. 不要なライブラリ禁止

標準機能または既存ライブラリで実装可能な場合、新しいライブラリを安易に追加しない。

ライブラリを追加する場合は、

「なぜ必要なのか」

を説明できる状態にする。

# 42. テスト

最低限、以下を確認する。

* 正常に出勤できる
* 二重出勤できない
* 正常に退勤できる
* 出勤せず退勤できない
* 1時間勤務の給与が時給と一致する
* 30分勤務の給与が時給の半分になる
* 時給変更後も過去給与が変化しない
* 同日複数勤務が正しく合算される
* 月間給与が正しく計算される
* 日付をまたいでも勤務時間が正しい
* ページ更新後も勤務中状態が維持される

# 43. ページ更新時

勤務中にページを更新・アプリを閉じても勤務状態を失ってはいけない。

再度開いた場合はDBから現在の勤務状態を取得する。

例：

10:00 出勤

11:00 アプリを閉じる

12:00 アプリを開く

↓

勤務時間

02:00:00

として継続する。

# 44. ブラウザを閉じてもタイマーを止めない

タイマーはブラウザ上で秒数を保存し続ける方式にしない。

DBへ保存された

出勤日時

と

現在日時

の差から勤務時間を計算する。

これにより、

アプリ終了
スマホ再起動
ブラウザ更新

が発生しても勤務時間を復元できる。

# 45. パフォーマンス

リアルタイム給与表示のためだけに毎秒データベースへアクセスしない。

リアルタイム表示はクライアント側。

勤務開始・退勤・データ保存・正式な給与計算はサーバー側。

という責務分担を守る。

# 46. 将来拡張を考慮する

将来的に以下の機能を追加できる設計にする。

* 休憩時間
* 深夜手当
* 残業手当
* 複数アルバイト先
* 日給
* 交通費
* 給料日予測
* シフト管理
* 月収目標
* 年収予測
* 扶養ライン管理
* CSV出力
* 給与明細
* 通知
* ウィジェット

ただし、現時点で必要でない機能を先回りして大量実装しない。

# 47. MVP優先順位

最初の完成版では以下を最優先する。

Phase 1

1. 時給設定
2. 出勤
3. 退勤
4. リアルタイム給与
5. 今日の給与
6. 勤務履歴
7. カレンダー
8. 月間給与

これらが正常に動作してから追加機能を実装する。

# 48. AIへの最終判断基準

実装方法に複数の選択肢が存在する場合は、

「ユーザーが毎日ストレスなく使えるか」

「給与計算の正確性を保てるか」

「初心者が後からコードを理解できるか」

「将来的に機能追加しやすいか」

の4点を基準に判断する。

このアプリでは、

高度な技術を使うこと

よりも、

シンプルで確実に動くこと

を優先する。
